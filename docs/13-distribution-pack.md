## How the pack is built (reproducible)

```
cmd.exe //c "Tools\Dist\rkc_make_dist_pack.bat"   # stage -> Dist tree -> hashes -> zip
bash    Tools/Dist/rkc_verify_dist_pack.sh        # extract, check hashes, run the extract
```

(Under this shell the batch needs `cmd.exe //c`, not `cmd.exe /c`: MSYS turns a lone `/c` into a
`C:\` path and the batch never runs. That trap cost one failed attempt.)

`rkc_make_dist_pack.bat` copies `Packaged\Windows`, excludes `CrashReportClient`, `Crashes` and
`Logs`, adds the notes, the guide and the pictures from `Tools\Dist\`, writes `SHA256SUMS.txt`
through `rkc_write_sums.ps1`, and zips with PowerShell's `Compress-Archive`. Two details in that
chain are load-bearing and were both found the hard way:

- `Compress-Archive` writes a zip that the `tar` shipped with this shell cannot read, so
  verification extracts with .NET's `ZipFile` (`rkc_extract_zip.ps1`), not `tar`.
- The pack's own manifest is regenerated by `rkc_write_sums.ps1` on every build, so its row count
  moves with the pack: 180 rows for 181 files (the file cannot list itself).
- `sha256sum` reads everything after the two spaces as the file name, so a `SHA256SUMS.txt`
  written with CRLF line endings fails with `No such file or directory` on every entry. The
  writer emits LF and ASCII explicitly. The first pack of the 20:00 increment had this defect;
  the verification step caught it, inspection had not.

## The guide pictures, and the manifest that was wrong

`Screens\` holds the seven pictures `FIRST_ROUND_GUIDE.md` embeds, and `CAPTURE_MANIFEST.txt`
ships with them to say where each one came from and what is in it. That manifest was rewritten
in this increment because it carried two defects.

**Defect 1 — the measurement table described a different run than the pictures.** The table's
numbers (121, 130, 217, 146, 1466, 227 distinct colours, and 1960/1903/2236/2037/3560/2083
light-text pixels) were measured on the files of capture run `20261019_201119`, while six of
the seven shipped pictures are the files of run `20261019_203256`. Both runs photographed the
same build, but a match frame differs between runs, so the table was evidence about files the
player does not have. Measured again on the shipped files, the front-end cards carry 67, 73,
160, 97, 204 colours and 211, 154, 486, 288, 337 light-text pixels. The corrected table is in
the manifest and in `Dist\screens_measure_fixed.json`; the tool that produces it is
`Tools\Diagnostics\verify_stage_shots.py`, which now measures the shipped folder with the
`manifest_kind: "capture"` rule (provenance, no HUD rows) as well as stage folders.

**Defect 2 — the pad-versus-match comparison was measured across two runs.** The old wording
compared a match frame from run A with the touch-pad frame from run B and read 114,895 differing
pixels (12.47%) as the pad's footprint. Part of that difference is simply the match having
advanced between the two runs. The manifest now gives both numbers and labels them:

| comparison | differing px | share | edge share |
| --- | --- | --- | --- |
| shipped pair: `05_match.png` (run A) vs `07_touchpad.png` (run B) | 114,895 | 12.47% | 78.5% |
| same-run control: run B `05_match.png` vs run B `06_touchpad.png` | 58,143 | 6.31% | 69.3% |

The decisive evidence that the pad is on `07_touchpad.png` is not either number: it is
`rkc_pad_presence.py` locating each of the six controls at the position the HUD's own layout
formulas predict, in the colour the HUD draws it, with a per-control ink count and a centroid
drift under 0.7 px (bar: 4.0 px) — and finding no pad in the run-A match frame. Two details in
that tool were wrong first and are fixed: the ring colours are converted from the HUD's linear
values to sRGB before matching (without it the five coloured buttons matched zero pixels), and
the search window is the ring's bounding box rather than a disc (a disc cuts the antialiased
stroke off-centre and reports a spurious +5..+8 px drift; the box reports under 0.7 px).

## Defect 3 — the "interactive playthrough" was scripted, and the row above is corrected

`START_HERE.txt` used to list `RKC_20261019_191803_match-end.txt` as an "Interactive human
playthrough", and this document's evidence table called it one too. That was wrong. The record
itself refutes it:

```
menu activity:       20 screen change(s), 0 accept(s), 0 back(s), 0 tap(s), 0 option change(s), 0 pause(s), 0 resume(s)
RESULT ROCKY BY KNOCKOUT | score 9-10 | 1 round(s) | 1193 ticks (19.88 s) | hits 0-13 attacks 0-13 blocks 0-0 dodges 0-0 knockdowns 0-0
```

The whole front end advanced while **no accept press, tap or option change was registered**. Only
the build's own scripted menu driver can do that: `FMachine::TickAutoPilot` calls `ActivateItem`
directly and never touches `Diag.Accepts`, whereas every human route into the menus — key, gamepad
or touch — increments one of those counters. The launch log names the switch outright (line 297 of
`Packaged\Windows\RockyKombat\Saved\Logs\RockyKombat-backup-2026.10.19-18.18.03.log`, sha256
`877a1b09…`):

```
LogInit: Command Line: -windowed -ResX=1280 -ResY=720 -nosplash -unattended -stdout -rkc.CaptureStages=1 -rkc.FrontEndAuto=3 -rkc.TouchForced=1 -rkc.QuickRules=1
```

It was an unattended capture run, and side A threw 0 attacks while the CPU threw 13. `Saved\Logs`
is excluded from the pack, so the lines that matter were copied into
`RockyKombat\Saved\Evidence\RKC_20261019_191803_launch-log-excerpt.txt`, which now ships beside
the record it explains, with the record's own lines re-quoted and the meaning of each stated.

The 28 match records in the pack's evidence folder now break down as: **24 records (every one from
18 October onwards) show a full front-end flow with 0 accepts and 0 attacks from the
human-configured side**, and 2 of the 4 older 17 October records are the only ones where the
player-controlled side produced input at all (2 attacks/1 hit/3 dodges and 1 attack, on that older
build, before the record had a front-end section). So the corrected claim is: the shipped build has
never had a person at the keyboard. The wording was fixed in `START_HERE.txt` and `KNOWN_ISSUES.txt`,
in `docs\06` (remaining work 3 and the "controls work" correction) and in `docs\07` section 2.3. The
pack was then rebuilt so the notes and the new excerpt travel together, and the rebuilt archive was
verified the same way as its predecessors: 181 files, 452,883,760 bytes, sha256
`d4c67c861ff29890141a1a7fb9ae9ab16d108bba6acdf8ebe9ac417e0da420ca`, 180 of 180 hashes OK, guide
checker 9 of 9, extracted self-test 219 checks / 0 failed at 22:00:40.

## What the pack deliberately does not contain

- **No Android APK.** See `docs\12-safearea-and-android-status.md`: the engine installation is
  missing its Android platform component (`Engine\Binaries\Android\` does not exist on this
  machine, re-checked 2026-10-19 20:20), and only the Epic Games Launcher can add it. The
  game-side phone work is implemented and asserted.
- **No installer and no code signing.** The game is a folder; `START_HERE.txt` says so and warns
  about the SmartScreen prompt.
- **No per-machine runtime junk.** Crash-reporter settings and logs stay out of the pack.
- **No claim of human playtesting.** `KNOWN_ISSUES.txt` states, in the same words as `docs\06`,
  that the 8-point checklist is unticked and that hit feel, blocking and dodging have not been
  judged by a person.
